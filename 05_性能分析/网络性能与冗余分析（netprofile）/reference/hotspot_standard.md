# 网络流量热点 · 严重度标准 (P0–P2，纯流量)

热点判断的权威标准,**由 agent 应用**。判据结合 UE/游戏 netcode 成熟实践 + 本项目实查配置。

> **终极目标**:看清**整个游戏过程的流量压力**、找出**降总流量压力**的杠杆。所以热点 = **压力**(全程/窗口流量够不够顶预算)+ **杠杆**(改哪里最省)。"该不该发"(浪费/可避免)是**冗余分析**的事,不在本标准。

> **分工(重要)**:判级是主观分析,归 agent。`hotspot.py` **只产出客观聚合数据**(各秒/各帧字节、各实体 bits/CPU/空跑次数、类别占比)和**纯算术比值**(×预算 / ×基线 / 占逻辑载荷%);**不分级、不排序、不下结论**。agent 读这些数据,按本文阈值判成 P0–P2(纯流量)、去重(如"某秒饱和"其实只是某突发帧的复述)、给根因与下一步。一致性来自**写死的量化阈值**,不来自脚本硬编码。(效率类 CPU/浪费不在本标准 → 见末尾, 归冗余分析)

## 度量口径(三种,别混用)
- **线上速率(wire)**:每帧 SocketSendTo 字节(压缩后真实线上量)→ 聚合成"**每秒 bytes/s**"。**用于 P0 饱和 / P1 关注**(它直接对预算)。**按秒/窗口看,不按单帧**——见下"为什么不单列字节突发"。
- **逻辑载荷(logical)**:每实体/类别的 bunch 内容 bit(压缩前)。**用于 P2 降压杠杆**(改哪里最省)。
- (复制 CPU `time_ms` 也在 token 里,但**不是流量**→ 归冗余分析(相关性浪费),不在本标准。)

## 基准常量(本项目, 配置实查)
| 量 | 值 | 出处 |
|---|---|---|
| 总带宽 TotalNetBandwidth | **32000 B/s** | `7UE/Engine/Config/BaseGame.ini`(在所有连接间分摊) |
| 单连接预算 B (动态) | **clamp(32000/N, 4000, 7000)** | MaxDynamicBandwidth=7000 / MinDynamicBandwidth=4000;N=连接数。1人=7000,4人=7000,8人=4000 |
| 硬上限 | 100000 B/s | `BaseEngine.ini` MaxClientRate |
| 复制 tick R | **30 Hz** | `BaseEngine.ini` NetServerMaxTickRate(项目 Config/ 未覆盖) |
| Reliable 缓冲 | **512 bunch / 每 ActorChannel** | NetConnection.h:57 + DataChannel.cpp:1094-1121(溢出→Connection->Close()) |
| 发送预算机制 | QueuedBits(超出排队、溢到后续 tick) | NetConnection.h:425 |
> **多连接口径(脚本已实现)**:`.nprof` 把所有连接聚合在一起,但**脚本按事件的连接号 `c` 拆开、每个连接各自判饱和**(预算 = 上面动态 B,按当次连接数算)。不再用"总量比单连接预算"那种错算。Reliable 缓冲按 **ActorChannel**(每 actor)独立。**P2 降压杠杆仍按全部连接汇总看**(优化一个属性/RPC 对所有连接都省)。
> Oodle 开(`DefaultEngine.ini` bEnableOodle=True)→ wire 是压缩后量、和 B 同口径可直接比;logical 是压缩前、只看占比。
> 本项目用自定义 `EMReplicationGraph`(ReplicationDriverClassName=/Script/EM.EMReplicationGraph), 相关性/优先级与原生不同 → 峰值成因结合它理解。

## 为什么不单列"单帧字节突发"(设计决策)
UE 用 **QueuedBits** 把单帧发送量跨 tick 摊开(NetConnection.h:425),bunch 还会跨帧缓冲、后续帧才 flush——**单帧字节大本身不直接卡死**。一个突发只有两种情况值得管,而它们都已各有归属:
1. **造成真实压力** → 它必然把所在的秒/窗口顶超预算 → **已被 P0 流量饱和(按秒)抓到**。秒/窗口(≈QueuedBits 排空尺度)才是对的单位。
2. **是可避免的浪费**(重复导出 / 整表重发 / 本可增量的全量同步)→ 这是**冗余**,归**冗余分析**(`/netprofile:redundancy`)。

所以本标准**不把"单帧 wire ≥ B"单独定级**(会误报加载边界的一次性 flush、且夸大严重度)。脚本仍输出"单帧尖峰"但**仅供定位**(去 GUI / `--range` 看),不是严重度。**例外是按条数算的"数量风暴"**(bunch/RPC 数量,见 P0 S2):数量爆棚会撑爆 per-channel reliable 缓冲→断线,即使总流量不高也阻塞,与字节体积无关。

## 严重度分级

### 🔴 P0 — 严重(可能卡死/掉线/丢包, 必修)
命中任一即 P0,按量化值排序:
- **S1 流量饱和**:**某连接**的某秒/1s 窗口 wire ≥ **B**(该连接动态预算)。→ QueuedBits 积压增长 → 延迟飙升、丢帧。严重度 = 速率 / B。**按连接各自判**(脚本输出"全程压力概况·每连接"),哪个玩家的连接超就报哪个。**全程视角**:看该连接"超预算秒数占其时段%"——占比小=偶发尖峰,占比大=结构性压力过高(终极目标主要盯这个)。
  - **判级前看上下文**:若饱和秒落在**加载边界**(同窗有 `*CloseLoading*`/`*DungeonRewards*`/大量 NetGUID 导出=一次性 spawn 潮),是加载期一次性流量、玩家无感 → 降级或标注"加载期,非 gameplay 压力"。
- **S2 数量风暴(撑爆 reliable 缓冲→断线; 也是业务 bug 信号)**:reliable 缓冲 = **RELIABLE_BUFFER=512 / 每 ActorChannel**(每个 actor 一条 channel,不是每连接)。源码:`NumOutRec + OutgoingBunches.Num() ≥ 512` 且 reliable → **`Connection->Close()` 直接断线**(`DataChannel.cpp:1094-1121`,注释"can't recover... send less stuff");未到上限也会触发"强制 reliable + 暂停该 channel 属性复制"的卡顿。**与字节体积无关**,即使总流量不高,数量爆棚也会阻塞。两个量化信号(脚本输出):
  - **单通道单帧 bunch 数**(按 token 的 channel 号 `ch` 精确到 channel):越接近 512 越危险。`NumOutRec` 跨未ACK帧累积,单帧数是**下限**。
  - **同种 RPC 单帧重复次数**(actor类::func):**≥约16次极大概率是业务设计 bug**——一个操作通常对应一个 RPC,短时间大量重复同种 RPC 几乎一定是调用点设计有问题;若该 RPC 是 reliable 还加速撑缓冲。⚠ class 级聚合:高次数可能是同一实例狂刷(真 bug),也可能多实例各发一次(可能正常)→ deep-dive/源码确认调用点是否单实例。
  - `.nprof` 无 reliable 标志 → 标为风险,deep-dive 查 UFUNCTION 可靠性 + 调用点业务语义。

### 🟠 P1 — 关注(高于常态 / 人变多易转 P0)
- 某连接的某秒 wire ≥ **k × 该连接基线**(其非0秒速率中位数,k 默认 **5**),但未达 P0(< B)。→ 压力还不大但远高于自身常态;**人数变多时 B 还会从 7000 往 4000 降(8人=4000),实体变多也会涨**,这类窗口最先转 P0。值得记一笔、不紧急。

### 🟡 P2 — 降压杠杆(改哪里最省, Pareto, 只看业务层)
"降总流量压力"的**主要可执行项**,**只列业务层、开发者真能改的东西**:
- 维度:**Top 属性(→`DOREPLIFETIME`)/ Top RPC(→`UFUNCTION`)/ Top Actor 类(→复制频率/Dormancy/裁剪)**。
- **占比按各自类别内算**(脚本 `pct_in_dim`):如"某移动属性 占属性流量 X%"、"某多播RPC 占 RPC 流量 Y%"——回答"谁主导这一类"。**15% = 重点高亮线**,不是触发门槛;无单项达 15% 仍报相对最大的几项。绝对字节同时给出(=改它能省多少)。
- **引擎结构不进交付分析**:句柄/内容块/NetGUID导出/未分类这些**业务层动不了**,只用一行"业务层 属性+RPC 占总 X%,其余引擎结构不计"交代,不itemize、不当杠杆。它们随你减属性/降频/降 spawn 自然下降。

> **引擎层背景知识(被问到才用,不进交付)**:逻辑载荷里那"其余 X%"是什么——
> 句柄=属性索引编码、内容块=子对象框架、NetGUID导出=对象引用入网(spawn相关)、**未分类=复制框架/初始spawn/结构开销**(属性句柄流+终止符、初始 actor 的 class/位置/旋转/缩放、bunch 控制位、跨帧 flush 残差)。
> **"未分类"不是 FastArray/自定义 NetSerialize**——那些走 `TrackReplicateProperty` 已记进"属性"(源码 DataReplication.cpp:1616)。这些都不是 ailog 的活(ailog 补的是"值变没变/业务场景")。

### (不在本标准)效率类:复制 CPU / 相关性浪费 → 冗余分析
**复制 CPU**(actor `time_ms`)和**相关性浪费**(被考虑复制但大多空跑——空跑=属性比对没发现变化、那次比对 CPU 白花)**不是流量、不在热点定级**。它们是"该不该发/比"的效率问题,归 `/netprofile:redundancy`(**③相关性浪费**,低优先、顺带提示,是否优化由开发者定)。push-model 免比对 / Dormancy 是其正解。

## 输出(agent 产出):统一的"排序热点清单"
agent 读脚本的客观数据后,产出 **按 P0→P2 排序的一张清单**(写进主报告 `AnalysisReport/<nprof>/hotspot.md` 的判级总表,纯流量;逐项细节在 `hotspot-<项>.md`),每条:
`[严重度] 类型 | 量化证据(指标值/倍数) | 定位(秒/窗/实体) | 风险或含义 | 下一步(--range深挖 / 源码 / ailog / 冗余分析)`
清单之外附:全程压力概况(超预算秒占比/峰值/常态)、流量去向(全类别)、时间线、各维度 Top(支撑细节)。**去重**重复指向同一事件的条目。**若全程超预算秒占比很低且峰值多为加载边界 → 直说"压力不高、无真 P0",别硬凑严重度**。效率类(CPU/浪费)不进本清单,顺带一句指向 redundancy 即可。

## 标准流程
1. `export` → 全量 JSON。
2. `hotspot` 概览 → 脚本算**流量客观度量**(全程压力概况、秒级速率+比值、降压杠杆、单帧尖峰仅定位) → **agent 据本标准判级排序出热点清单** + 支撑细节。**只列不深入。**(效率类 CPU/浪费 看 redundancy)
3. 开发者挑一条 → `hotspot --range A B` 定窗取完整构成。
4. 结合源码推理 → 源码能定就改(降压杠杆改法);要业务场景语义("这波在干嘛/值变没变")才用 ailog。未分类高=复制框架/spawn,看该窗 ReplicateActor 在 spawn 什么;尖峰疑似可避免 → 冗余分析。

## 量化阈值(agent 套用)
`B=7000 B/s, R=30Hz, RELIABLE_BUFFER=512(预警≥256), P1=5×基线, P2=15%逻辑载荷(高亮线非门槛)`。
阈值是工程约定、可按项目调(改本文即可,脚本不含阈值);分级"含义"(P0=会出事 / P1=关注 / P2=降压杠杆)不变。
> 效率类阈值(浪费 考虑≥50次且空跑≥80%)在冗余侧(③相关性浪费),不属本流量标准。
