# netprofile — 网络性能分析套件（知识库）

本文件是 **被命令加载的共享库**，不是入口。入口是命令：`/netprofile`（全流程）、`/netprofile:export|hotspot|redundancy`（单步）。

## 定位与契约
- 一套规范化、半自动的 `.nprof` 网络性能分析流程：导出 → 热点(整体全貌) → 冗余(候选)，先粗定位、再深挖。
- **输入** = 一个 `.nprof` 路径；**输出** = 写进 `AnalysisReport/` 的 MD 分析报告（**先逐项分项 md、后主报告总览+导航**），不是堆在对话窗口（见"★MD 分析报告产出规范"）。
- **全量 JSON（体量大）只给 python 脚本读、绝不喂 AI**；命令把它提炼成 KB 级小 JSON / 文本给 agent 看。
- 解耦：export 是唯一解析 .nprof 处（无损 1:1）；hotspot/redundancy 各自从 events 聚合自己要的口径。

## ★分析铁律（深度优先 + 分段确认 + 必读源码）—— 目标是深度优化网络压力,不是出浅表摘要
1. **三段分开、各自吃透,阶段间用户确认门**：导出 → 热点分析 → 冗余分析,**一段做完出完整报告就停,等开发者确认再进下一段**。**绝不把热点+冗余揉成一份合并快报**——那样每个点都浅尝辄止、发挥不出 agent 能力。热点与冗余是两种不同分析(压力 vs 该不该发),必须分开深做。
2. **每段都要深,不是"Top 表 + 一句话"**：
   - **热点段**：先铺**整体网络压力全景**(总发送/常态/峰值/超预算秒占比/时间线形态解读——稳定高压?偶发尖峰?战斗节奏?),再逐级 P0/P1/P2 判+量化证据+上下文,再对 P0/重点用 `--range` 深挖那一窗的真实构成。
   - **冗余段**：逐个高价值候选用 `--prop` 深挖发送画像(谁在发/节拍/体积)。
   - 把"**为什么高、是不是真问题、改了会怎样**"讲透,而不是报个占比就完。
3. **必读源码,不靠占比下结论**：看到一个大占比的 RPC/属性,**不能直接说"要优化"**——大占比**可能只是高集成**(如一个多播一次发很多特效=好设计),也可能是真浪费。**必须去读它的业务源码**(RPC 的 `UFUNCTION` 声明+调用点、属性的 `DOREPLIFETIME`+赋值处、Actor 的复制设置),结合业务判断"真可优化 / 还是合理同步"。**结论 = 数据 + 源码,缺一不可;只有数据没源码 = 不合格。** 源码搜索遵循仓库 Combat/网络优先范围。
   - **★"它是蓝图 RPC/属性" ≠ 源码不可读**:其**声明/实现/管线几乎都在 C++ 基类或效果管线里**(如 `MulticastPlayEffectResults` 的实现、`TickSkillEffectResult` 批量、`AddEffectResult`/`AddEffectResultImmediate` 都在 `Source/EM/.../Combat/`)。grep RPC/属性名 + 相关管线词,**必须读到、必须解释机制**(频繁同步?批量?逐对象?有无破批量的 immediate 路径?)。**不许拿"是蓝图多播"当借口跳过机制源码。**
   - **只有 payload 的运行时 per-Type 构成**(这条多播里到底是 Damage 还是 PlaySE/FX、各占多少)才是源码也给不出、需 ailog 的;且**先查项目是否已有该探针**(本项目这条 RPC 已有 `AIDeBugBuildMutiEffectTraffic` + `PATHB_*`,开 `gm aidebuglog` 即可,不用新铺)。
4. **★引用记忆/`.agents` 里的结论 = 带来源、不当事实**：那些是**参考、且常带"场景相关/单局/待重测"的免责**。引用时必须**原样带【出处 + 原始免责 + 适用范围】**,**绝不抹平成"真实战斗里就是这样"的普适事实**。对"**当前这份 capture**"下结论,只能基于**当前数据**或**当场核的源码**;数据看不到的(如 RPC payload 内部 Type/具体技能效果)→ 走 ailog(用户确认,见下),**不靠搬旧测量充数**。(反面教材:把 `.agents` 一条"某局 100% Damage、原文标了待重测"的记录,当成事实写进报告。)
5. **★报告自底向上、完整自洽(可单独看)**：不是"空降一个判级"。顺序 = **先摆数据证据**(峰值帧 → 峰值区间[秒/数秒,逐窗取构成] → 场景/分局[按换关/换局分段] → 整体全景),**再源码推导**(这几个 top 属性/RPC 是什么、为什么重:频繁同步/数量过多/设计冗余/高集成),**最后才落判级结论**(结论是推导的自然落点、不空降)。**允许分析慢**(多窗 --range、读多处源码),用户接受等待,但**每段都要扎实**,最终拼成证据→推导→结论闭环、不看原始数据也信服的完整报告。详细分段见 hotspot/redundancy 命令文档。
6. **★所有需开发者决策的节点,一律用结构化选项呈现(`AskUserQuestion` 工具),不用 prose 让人打字猜**。贯穿整个流程的每个 gate:模块侧重(多选)、**热点报告后的下一步**、**冗余报告后的下一步**、是否接 ailog、json 保留策略——全部给选项(每项写清"做什么"),该多选的多选。不要写成"要我继续吗?/想深入哪个?"那种自由文本。

## ★这是超大型任务（务必当超大型任务做：显式规划 · 动态拆分增补 · 逐项起 subagent）
`/netprofile` 全流程——尤其热点+冗余的**逐项全覆盖深挖**——是**超大型任务**，不是一两个回复能收的。agent 必须**清醒意识到这一点**，并按超大型任务的方式组织自己：

1. **显式规划任务清单（用 `TaskCreate` / 任务列表）**：导出后先建任务骨架——每个阶段、每个待调查的属性/RPC/actor 各是一个任务；逐项 in_progress→completed，进度对开发者可见。**别靠脑子记、别一把梭。**
2. **动态拆分 + 动态增补（关键：不是开局拍死一个静态清单）**：
   - **拆分**：某项发现问题多/复杂 → 当场拆成更细的子任务（如某热点 RPC 拆成「读 UFUNCTION 声明 / 查调用点是否逐对象 / 审合批时序副作用」）。
   - **增补**：分析中冒出新的可疑项/新线索 → **新增任务**，让清单随认识增长。**实时分析驱动任务演化。**
3. **逐项调查起 subagent（省主上下文 · 可并行 · 能挖深）**：每一项的"读源码 + 业务语义"**专门起一个 subagent**（`Agent` 工具，`Explore` 或 `general-purpose`）去做——它 grep `UFUNCTION`/`DOREPLIFETIME`/调用点/相关管线、读 C++/Lua，回报「它是什么、谁在发、为什么发、业务语义、能不能改」。主 agent 当**规划者/协调者**：派活、收结论、做第③类优化追问、写分项 md。
   - 好处：① 主 agent 上下文不被单项源码细节塞满 → **扛得住超大型任务全程**；② 多项可**并行**派 subagent（一条消息多个 Agent 调用）；③ 子 agent 专注一项能**搜透**。
   - 主 agent 仍要对子 agent 的结论**把关**，别照单全收：结论 = 数据 + 源码，缺一不可（铁律3）。遵循仓库 Combat/网络优先搜索范围（见 `.agents` 规则），别让 subagent 全仓乱扫。

## ★逐项闭环调查（热点/冗余两段共用的深度方法 —— 报告有没有深度，全看这一步落没落实）
报告浅的根因 = 把"分析"当成一次扫描 + 在对话窗口一把梭收尾（读两三个源码就外推全部）。深度不靠"应该深入"的口号，靠**结构强制**。这一节是热点段、冗余段**共用**的执行内核，两段的命令文档都指回这里：

1. **建清单，全覆盖、不抽样** —— 开段先把所选 scope 内的业务项（逐属性 / 逐 RPC / 逐 actor 类）列成**分项待办清单**：**只要不是明显消耗极低的，都列上**（噪声地板以上全要），**不是只取 Top-N**。深度的前提 = 一个都不跳、不靠采样几个就外推全部。**最危险的恰恰是"看着消耗还行、其实冗余不少"的中等项**——top-N 会漏掉它们，堆起来后期最难维护。本场景**不怕慢、不怕 token，怕漏、怕错**。
2. **每一项都走同一套"三步吃透"（通用，与它具体是什么无关）**：
   - **① 数据画像** —— 从脚本取该项客观画像：总量/占比、单帧次数、出现率、by-actor 分布、发送跨度。
   - **② 读源码（起 subagent 去搜，见"★这是超大型任务"）** —— 派一个 `Explore`/`general-purpose` subagent 搜这一项的源码 + 业务语义：属性读 `DOREPLIFETIME*`+赋值处；RPC 读 `UFUNCTION`+调用点；actor 读复制配置。搞清"它是什么、谁在发、为什么发"。**"是蓝图 RPC/属性"≠ 不可读**（实现/管线几乎都在 C++ 基类或效果管线，grep 名字+管线词必能读到机制，见铁律3）。主 agent 收子 agent 结论后把关，不照单全收。
   - **③ 语义 + 优化追问（深度的来源，读完定义不许停）** —— 每项必答这组**通用问句**：
     - 这个量是 **【单位贵】还是【数量多】**？—— 任何聚合量先拆成 *单位 × 数量*，看是单只/单次本身重、还是实例多堆出来的（两类问题改法完全不同）。
     - **发送模式能不能改**？—— 过一遍"通用优化菜单"（见下节）：合批 / 降频 / `COND_*` / push-model / 量化 / 可靠性 / Dormancy / 相关性裁剪。
     - **改了语义/时序会不会变**？—— 会变吗？哪些场景变、哪些不变、副作用是什么？（尤其合批：多次合一次可能改接收端时序/中间态，**但不一定**，按具体场景判，不机械合批。）
     - **结论三档** —— ✅ 可优化（给改法 + 预估收益 + 副作用） / ❌ 合理设计（说明为何，排除） / ❓ 源码看不准（走 ailog 确认，见"ailog 集成"）。
3. **每个值得深挖的项各写一篇分项 MD（`<段>-<项>.md`）** —— 空/薄的文件一眼就是缺口，逼着补。不在对话窗口堆结论（载体与"先分项后总览"的产出顺序见"★MD 分析报告产出规范"）。
4. **循环到 scope 内所有项走完，再回头生成主报告做总览+导航**，这段才算结束。

> 这组通用问句会自然推出该有的深度，**不要再为个案堆特化规则**。举两个**示例**（只演示"一项被吃透长什么样"，非规则）：一个 RPC 单帧调了多次 → 第②类追问"能不能合批"自然带你去读调用点、看是不是逐对象调；某种怪流量高 → "单位还是数量"自然逼你按只数归一（是单只贵还是只数多）。闭环走到位，这些结论自己会冒出来——脚本抛的阈值信号（均次/帧、出现率、空跑率…）只是**起点**，不是判决。

## ★模块侧重选择（导出后、热点分析前必问；多选 —— 防巨无霸遮蔽分析）
**为什么必须先选**：DS 战斗场景里**技能效果 RPC(effect-result 多播)通常占总流量 80%+**,高度集成。不区分的话,它会把其它模块压成个位数%、让分析被它**遮蔽/偏移**——其它可优化项被忽略、报告还卡在它身上(它必要+已优化、砍不动)。所以**导出后、热点分析前,先让开发者多选侧重哪些模块**,并把上面这个"为什么"讲给开发者听。

选项(多选):
- **① 战斗效果侧**(技能效果 RPC):effect-result 多播本身;其内部 Type 构成需开 `gm aidebuglog` 拆(选它才需 ailog)。
- **② 怪物/AI 侧**:怪/召唤兵 actor(`BP_Mon_*`/`BP_Eve_*`)的属性同步 + 它们的 RPC。
- **③ 关卡/场景侧(含 GameMode/GameState)**:关卡/环境 actor、`BP_EMGameState`、spawn 潮、NetGUID 导出。
- **④ 玩家/角色侧**:玩家/幻象 actor(`BP_PlayerCharacter`/`BP_PhantomCharacter`)的属性+RPC。
- **⑤ 移动/位置(跨类)**:`ReplicatedMovement`/`RepRootMotion`/transform 时间戳/相机位。

**所选模块热点段和冗余段都用(同一套侧重,选一次两段通用)。** 冗余段同样:巨无霸单列、候选/结论只在所选模块内挑、被排除的效果 RPC 不当头号候选。

**怎么用(分工:筛选在 agent 推理层,不进脚本)**：脚本照常输出全量客观数据;**agent 据所选模块在数据上做"头尾分治"**——
- **头**:技能效果 RPC 这个巨无霸**单列**(标"另一条专门的优化线、需 ailog"),**不让它霸占 Top 榜**。
- **尾**:对**所选模块**(用 actor 类名/属性名/RPC 名归类)**聚焦深做**——峰值窗里这些模块发了什么、读源码、判级;**剔除巨无霸后对所选范围重新看分布**,让小模块浮出来。
- 没选的模块:一句话带过,不深挖。只有选了"①战斗效果侧"才对 effect-result 开 ailog(用户确认),其余视角跳过它。
- **★判级也按所选模块范围(关键,别违背开发者的排除)**:P0/P1/P2 **只在所选模块内判**。被排除的巨无霸(技能效果 RPC)**即便是整体饱和的主因,也不在本报告判级、不写成 P0**——它只在"全程压力全景"里一句话交代(整体饱和主要由它撑着、但它是你**已排除**的另一条专门线)。**所选模块本身不造成饱和,就直说"所选模块内无 P0"**,绝不把开发者刚排除掉的东西又拎回来当报告的 P0 头条。(反面:开发者只选了怪物/玩家,报告却 🔴P0=技能效果饱和。)

## 本套件看不到什么（认知边界，必须诚实告知，别把"无 P0"当成"网络健康"）
NetworkProfiler `.nprof` 本质是**服务器发送带宽 + reliable 缓冲**记录。**它看不到**：
- **接收侧开销**（客户端收包/反序列化代价）；
- **延迟 / 抖动 / 丢包 / RTT**（只有发了多少，没有到没到、什么时候到）；
- **相关性的"正确性"**（只看"发了却没用=浪费"，看不到"该发的漏发了"）；
- **RPC 时序 / 可靠性 bug**（顺序错、该 reliable 没 reliable，这里看不出）；
- **服务器复制 CPU 全貌**（只有每 actor `time_ms` 这一个粗量）。
→ 出报告时若"无 P0"，要说"**发送带宽与缓冲层无紧急项**"，而不是"网络健康"——上面这些维度本工具压根没覆盖。

## 分析方法论：两段式（压缩定位 → 定向深挖）
全量 JSON 几十 MB，**agent 上下文有限、不可能整吞**——这是 hotspot/redundancy 都用"过滤聚合脚本"的根本原因：
1. **压缩定位**：脚本把全量压成 KB 级"分布数据"（hotspot=热点帧/流量去向；redundancy=冗余候选），从总量上锁定方向。
2. **定向深挖**：锁定后回全量、**只取相关那一小块**的完整数据（hotspot 定帧/窗、redundancy 定属性），结合源码推理。
- **全程只把小文本/小 JSON 给 agent，全量只给 python。**
- 深挖出的数据要**完整**（不漏类别/事件），否则推不出真因；但呈现要**紧凑**（聚合 + Top-N，不 dump 原始流）。
- 源码能定就直接改；要业务场景语义("值变没变 / 这波在干嘛")才接 ailog。"未分类"高 = 复制框架/初始spawn/结构开销居多(**不是** FastArray/自定义序列化——那些被 token 记了),随减属性/降 spawn 自然降,不是 ailog 的活。

## ★MD 分析报告产出规范（AnalysisReport/ —— 这才是给人看的交付物）
深度分析的产物**写进 MD 文档**，不堆在对话窗口（对话模式逼 agent 一把梭、读两个源码就外推，是报告浅的主因之一）。
```
<agent>/skills/netprofile/AnalysisReport/<原nprof文件名>/
    ├── hotspot-<项>.md       # 【先产出】逐项详尽分析: 某属性/RPC/actor 的完整逐项闭环
    ├── redundancy-<项>.md    # 【先产出】逐候选详尽分析
    ├── hotspot.md            # 【后产出】热点主报告: 压力全景 + P0/P1/P2 判级总表 + 导航到各 hotspot-<项>.md
    └── redundancy.md         # 【后产出】冗余主报告: 总览 + 导航到各 redundancy-<项>.md
```
**产出顺序（重要）：先分项、后总览。**
- **第一步：逐项各成一篇** —— scope 内每个值得深挖的业务项，各写一篇**完备**的 `<段>-<项>.md`（就是"逐项闭环调查"的载体：数据画像 → 读源码 → 优化追问 → 三档结论）。一项一文件，逼着每项写到位、互不挤占。
- **第二步：主报告做总览+导航** —— 所有分项写完后，再生成 `hotspot.md`/`redundancy.md`：**压力全景/候选总图 + P0/P1/P2 判级总表 + 链接导航到各分项 md**。主报告偏"索引 + 结论汇总"，细节在分项里、别在主报告重复展开。
- **小项可不单列**：一眼判 ❌合理/无问题、不值得展开的项，主报告里一行带过即可，不必单开文件（避免文件爆炸）。值得深挖的才各成一篇。
- **AnalysisReport（交付物，默认留） vs json（中间数据，可删）**：`json/` 是给脚本/深挖用的中间产物；`AnalysisReport/` 是给人看的报告。收尾保留策略**两者分开问**。
- `<agent>` = 各 agent 根（Claude=`.claude`/Trae=`.trae`）；一次 capture 一个子文件夹，名 = 原 nprof 去扩展名。

## 热点分析（统一口径就叫"热点分析"；严重度标准 P0–P2 权威定义见 `reference/hotspot_standard.md`）
**含义(展示给开发者时要说清)**：热点分析看的是网络流量**【压力】**——哪些时段/actor/属性/RPC 发得多、压不压得住带宽预算(P0/P1/P2)。**别造别名(流量分析/压力分析之类),口径统一叫"热点分析"。**
**与冗余分析的分工(两段描述别重合)**：**热点=「发得多不多、压不压得住」(压力视角)**;**冗余=「该不该这么发、发送模式能不能改」(同步设计视角)**。"该不该发"(浪费/可优化)一律归冗余分析。
**终极目标**：看清**全程流量压力**、找**降总压力的杠杆**。热点 = 压力(够不够顶预算) + 杠杆(改哪省)。
**分工**：`hotspot.py` 只产出**客观聚合数据**（全程压力概况、各秒速率+算术比值、降压杠杆、CPU、浪费、单帧尖峰仅定位），**判级是 agent 的事**——agent 读数据、按本标准量化阈值判级、排序、去重、给根因。一致性来自写死的量化阈值，不是脚本硬编码定性结论。
agent 产出**按严重度排序的一张热点清单**：
- **🔴 P0 严重（会卡死/掉线/丢包）**：① 流量饱和——**某连接**的某秒 wire ≥ B（**按连接各自判**，B=clamp(32000/N,4000,7000)：1~4人=7000，8人=4000）；全程看该连接"超预算秒占比"；**判前看上下文**，加载边界(CloseLoading/spawn潮)的一次性流量要降级。② 数量风暴——撑爆 reliable 缓冲(**512/每 ActorChannel**, 溢出→`Connection->Close()` 断线, DataChannel.cpp:1094)。两信号:**单通道单帧 bunch 数**(越近 512 越危, NumOutRec 跨帧累积)+ **同种 RPC 单帧重复**(≥约16次极可能业务bug:一操作应一RPC)。与字节体积无关、总流量不高也会阻塞。须查 UFUNCTION 可靠性+调用点。
- **🟠 P1 关注**：某秒 wire ≥ 5×全程基线 但 < B。单客户端压力还不大，但多客户端/多实体时最先转 P0。
- **🟡 P2 降压杠杆（Pareto，"改哪最省"，只看业务层）**：只列 Top 属性(→DOREPLIFETIME)/RPC(→UFUNCTION)/Actor类，**占比按各自类别内算**(谁主导属性/RPC流量)。**15%=重点高亮线**。引擎结构(句柄/内容块/NetGUID导出/未分类)**不进交付分析**——只用一行"业务层 属性+RPC 占总 X%，其余引擎结构不计"交代;业务层动不了、随减属性/降spawn 自然降。它们具体是什么见下"引擎层背景知识(被问到才用)"。
- **❌ 不单列"单帧字节突发"**：UE 用 QueuedBits 跨 tick 摊发、bunch 跨帧缓冲，单帧字节大不直接卡死。突发要么体现为窗口饱和(=压力,已被 P0 抓)、要么是可避免浪费(→冗余分析)。脚本"单帧尖峰"仅供定位、非严重度。例外=Reliable 风暴(按条数，见 P0)。
- **❌ 不含效率类(复制 CPU / 相关性浪费)**：这不是流量、是"该不该发/比"的效率问题 → 归冗余分析(相关性浪费)。热点只管流量(P0/P1/P2)。
> 度量三口径别混：**wire**(SocketSendTo 压缩后字节，对预算→P0/P1) / **logical**(bunch 内容 bit 压缩前，看占比→P2) / **CPU**(time_ms→归冗余, 不在热点)。
> 多连接：`.nprof` 把所有连接聚合，但**脚本按事件连接号 `c` 拆开、每连接各自判饱和**（DS 支持 4 人、后续更多）；预算 B 按当次连接数动态算。P2 降压杠杆仍按全部连接汇总。阈值改 `reference/hotspot_standard.md`（脚本不含阈值）。

## 冗余分析（统一口径就叫"冗余分析"；全落到源码定义的 属性/RPC/actor）
**含义(展示给开发者时要说清)**：这里的"冗余" **≠ 字面"白发"**——绝大多数流量是该发的;冗余分析找的是**同步设计上可优化的发送模式**(逐对象 RPC 可合批 / 高频可降频 / 值少变可 push-model / 相关性浪费)。不要把名字换成"同步优化分析"之类,**口径统一叫"冗余分析"**,含义靠这句说明。
**下面三类是脚本据阈值抛出的【起点信号】(候选，不是判决)** —— 每条都必须走"★逐项闭环调查"读源码吃透才下结论，别拿信号本身（均次/帧、出现率、空跑率…）当结论。三类信号：
- **① RPC 合批候选**：同种 RPC **均次/帧 ≥2**（=帧内多次调用）→ 疑**对多个对象逐个调 RPC**（几帧内高频，参数多半重复）→ 合并成一次**数组/多播** RPC。`const_size`(每次大小恒定)加强"参数齐整可合批"。落 `UFUNCTION` 调用点查是否在循环里逐对象调。**这是本分析最有价值的一类**（多人战斗常见）。
- **② 高频同步候选（属性/RPC，降频/push）**：属性高频(出现率高)→ 降频 / 客户端推导 / `COND_*`；恒定且值少变 → push-model `MARK_PROPERTY_DIRTY`。RPC 周期高频(均次/帧≈1) → 降频。
- **③ 相关性浪费（actor，真'白发'，少见，低优先）**：actor 被考虑却 ≥80% 空跑(pending=0，比对没变化白花 CPU)→ push-model/Dormancy/降频。脚本附复制 CPU 量化（关联 .agents 需求 DEM-NET-CharacterBasePushModel-001）。
- **突发归口**：热点的"单帧尖峰"若疑似可避免（重复 NetGUID 导出/整表重发/本可增量的全量同步）→ 在此确证。
> **核心限制**：`.nprof` 只记"发了什么"、不记"**是否需要发/值变没变**"；本项目未开 comparison tracking → **只给候选不下定论**。确证靠：源码看 `UFUNCTION` 调用点/`DOREPLIFETIME` 条件，或 `battle:ailogverify` 测值变没变。
> 类级聚合限制：RPC 只有 actor *类*不是实例，"均次/帧高"是"逐对象"的强代理(单实例每帧调同 RPC 多次本身也odd)，但不能 100% 证不同实例 → deep-dive 确认。

## ★交付分级（统一 P0/P1/P2 — 出报告时把热点+冗余合成一张清单）
两者严重度轴不同:**热点=紧急性(会不会崩),冗余=收益(能省多少)**。最终交付**合并成一张按 P0→P2 排序的清单**——**紧急性定 P0,重要性(收益×确信×成本)定 P1/P2**。agent 据脚本客观数据判(沿用分工铁律:脚本给量、agent 判级)。

| 级别 | 判据 | 典型来源 |
|---|---|---|
| 🔴 **P0 紧急(必修,会出事)** | 游戏会卡死/掉线/丢包 | **仅热点**:流量饱和(秒≥B,真实压力非加载边界) / 数量风暴(撑爆 reliable 缓冲→断线)。**冗余不进 P0**(它找的是"能省"不是"会崩") |
| 🟠 **P1 重要(排期修)** | ① 压力预警 ② 高收益+**已确认可改**的优化 | 热点 P1(≥5×基线/多人易转P0) + **源码确认**的冗余(确认的逐对象RPC→合批省一大块、确认的高频属性→降频/COND/push) |
| 🟡 **P2 优化机会(按 ROI 做)** | 收益中 / **未确认的候选** / CPU收益 | 热点降压杠杆(Pareto) + 冗余候选(未源码确认的合批/降频/push) + 相关性浪费(低优先) |

**判级输入**:紧急性=超预算/撑缓冲(热点P0信号);重要性 = **收益**(带宽KB/调用次数,脚本给) × **确信度**(冗余全是候选→**未源码确认默认压 P2,确认后升 P1**) × **成本**(合批易/push-model重,agent 看源码估)。
**每条格式**:`[P级] 类型 | 量化证据 | 定位(actor/属性/RPC/秒/帧) | 影响 | 改法/下一步(源码 / --range / --prop / ailog)`。
**报告结构**:先 P0→P2 合并清单,再附支撑细节(全程压力概况、Top 表)。**全程压力不高且无 P0 时直说"无紧急项",别硬凑**。

### ★报告必须自解释(给不懂本 skill 的人也能看懂)
报告读者(策划/其他工程师/leader)**不知道本 skill 的口径**。所以**每份交付报告必须自带一段"口径速查",解释清楚术语、数值怎么来的、P 级具体含义**——不能裸抛"×3.2预算 / P0"让人猜。把下面这段(按实际数填)放进报告(开头或结尾):
```
口径速查
· 预算 B：单个客户端连接的带宽预算 ≈ <B> B/s（来自引擎 BaseGame.ini 的 MaxDynamicBandwidth，
  按当次连接数 N 动态分：B=clamp(32000/N,4000,7000)，1~4 人都约 7000）。"某秒超预算"=该秒服务器
  发给这个连接的字节 > B；服务器每秒按 tick 30Hz 发。
· ×预算 = 该秒速率 ÷ B（几倍预算，>1 即超）；×基线 = ÷ 该连接平时常态速率（几倍于自己平时）。
· 占比：属性/RPC 后面的 % 是"占该类总流量"（谁主导这一类），不是占全部流量。
· 严重度（紧急性→P0，收益×确信→P1/P2）：
  🔴 P0 = 会卡顿/掉线/丢包，必修（持续超预算 或 撑爆 reliable 缓冲断线）
  🟠 P1 = 暂不严重但要关注/排期（高于常态、多人易恶化；或已源码确认的高收益优化）
  🟡 P2 = 优化机会，按收益做（降压杠杆 / 未确认的冗余候选）
```
> 数字别只给比值,**带上绝对值**(如"22.17 KB/s,是预算 7000B/s 的 3.2 倍"),让人不查标准也懂量级。术语首次出现时**就近一句话解释**。

## 通用优化菜单（"逐项闭环调查"第②类追问"发送模式能不能改"时逐项套用；遵循仓库 Combat/网络优先范围）
不是特化规则，是每一项读完源码后**都过一遍**的候选改法清单——哪条适用由该项的源码+语义决定：
- 属性 → `GetLifetimeReplicatedProps`/`DOREPLIFETIME*`：降频 / `COND_SkipOwner|InitialOnly|SimulatedOnly` / push-model `MARK_PROPERTY_DIRTY` / 量化 `FVector_NetQuantize` / `TArray`→`FFastArraySerializer`。
- RPC → `UFUNCTION` 声明：合批（逐对象→一次数组/多播） / 降频 / 改可靠性 / 挪属性复制；多播是否 `Reliable`（最贵）。**合批务必审时序副作用**（见闭环第②类）。
- Actor 复制耗时高 → `NetUpdateFrequency` / `NetDormancy` / 相关性裁剪（本项目用 `EMReplicationGraph`）。
- **数量驱动型**（某类 actor/RPC 因实例多而总量高，非单只贵）→ 优先**减少实例 / 同类批量同步 / Dormancy / 相关性裁剪**，而非抠单只字节。

## ailog 集成（业务语义缺口的外援；必须用户确认、可跳过）
**① 触发时机(主动识别,别错过)**：`.nprof` 看不进**业务语义**、而你又需要它才能下结论时——典型:
- 某 RPC/属性 payload 内部构成(如 `MulticastPlayEffectResults` 里到底是 Damage 还是 PlaySE/FX、具体哪个技能效果);
- 冗余候选"值是否真在变"(push-model 判定);
- 某高压窗"这波业务在干嘛"。
**此时不许猜、更不许搬记忆/`.agents` 旧结论充数(见铁律4)。正确动作 = 提示开发者:可用 ailog 拿运行时业务日志来拆。**

**② 机制(不依赖 ailog skill 是否安装)**：AI 日志**协议已在代码库**——入口 `Content/Script/AIDebugLog.lua`、C++ 机制 `Source/EM/Public/Common/AIDeBugLogProtocol.h`(探针 `AI_PROBE`/`_G.AIProbe.Log`、常驻 `AI_DEBUG_LOG`、总开关 `gm aidebuglog`)。
- **装了 `battle:ailogverify` skill** → 用它(加探针+跑测+验证+清理一条龙)更省事。
- **没装也能做** → 直接按协议接入:在目标业务路径(如 effect-result 发送处)铺 `AI_PROBE` 探针 → 引导开发者跑测 → 读 `Saved/Logs/EM*.log` 的 `[AIDeBug_*]`。

**③ 必须用户确认、给选项(不要自作主张去跑)**：开发者**可能根本不关心这一块**(如只想看属性/移动,不在乎技能效果 Type 构成)。所以**先问、给选项**,例如:
- ① 用 ailog 拆这个 RPC 的业务构成(铺协议探针 / 或用 ailog skill);
- ② 跳过,这块如实标注"nprof 看不到、未拆",继续看其它;
- ③ 只在源码层给结构性可能(不下定量结论)。

**桥接口径(真要做时)**:**按时间、不按帧号**——`.nprof` 帧=FrameMarker(带 RelativeTime 秒)、ailog=`GFrameCounter`,不同源;用 nprof 高压窗的 RelativeTime(+进程起始)对 `[AIDeBug_*]` 同时段。netprofile 本身不依赖 ailog。

产出 `<Project>/Saved/Profiling/<Game>-Pid<pid>-<时间>[n].nprof`。需 Development/Debug 构建。
