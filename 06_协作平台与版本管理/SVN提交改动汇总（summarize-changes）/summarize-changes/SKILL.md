# 整合修改与代码审查

根据多次 SVN 提交日志，取最终状态，输出核心改动与测试点，并对净改动进行代码审查。

> **路径配置**：本文件中的 `{EM_ROOT}` 等占位符请先从 `.skill\CONFIG.md` 读取实际值。

## 触发条件

- 要求总结提交、整合修改、输出改动和测试点
- 输入来源有两种，都能触发：
  - **只提供链接**：用户给出 TAPD 需求链接（含 story/bug ID），没有贴提交日志
  - **提供详细内容**：用户贴出提交日志（版本号 + 文件列表 + commit message）

## 工作流程

1. **定位提交**，根据输入来源分两种情况：
   - **用户提供了详细内容（版本号 + 文件列表）**：直接用，跳到第 2 步。
   - **用户只提供了链接**：主动用 `svn log` 搜索，不要反问用户要日志。从链接中提取 ID（如 `1131626021001320439`），范围必须拉到最近 **1000** 次提交，因为同一需求可能跨多天、间隔数百个版本提交多次（用 `-l 100` 会漏掉）。命令：
     ```
     svn log -l 1000 --search "<ID>" {EM_ROOT}
     ```
     搜索匹配后，对每个命中的版本用 `svn log -r <版本号> -v {EM_ROOT}` 取文件列表。
   - 注意 `--search` 匹配整条 message，链接 ID 与提交 message 里的 TAPD 路径一致即可命中；如多次提交 message 文案不同，可补充关键词（如需求标题）做 OR 搜索。
2. **取净改动 diff**：对每个文件，取最早版本到最新版本的 diff：`svn diff -r <最早版本-1>:<最新版本> <文件路径>`。这样得到的是净改动，而非每次提交的中间状态。多个文件可写在同一条命令里。
3. **分析 diff**：理解实际的代码改动，判断每个文件做了什么、提供了什么能力。
4. **交叉验证**（审查核心，不可跳过）：diff 只显示"改了这几行"，但真实影响取决于全树谁还在用被改动的符号。必须验证：
   - 用 `rg` 搜索 diff 中被移除/改名的标识符在新/旧全树的引用，确认没有残留调用点。
   - 验证 require / include 的增删是否对称：新增的依赖是否真的用到，删除的依赖是否不再被引用。
   - 检查 require 链是否存在循环依赖。
5. **输出总结 + 审查**：按输出格式组织，先给改动总结与测试点，再给代码审查结论。

### diff 获取

svn diff 是已批准的命令前缀。网络访问可能被沙箱拦截，失败时用 `require_escalated` + `justification` 重试：

```
svn diff -r <prev>:<rev> <文件路径1> <文件路径2> ...
```

如果文件在最早版本不存在（新增文件），diff 会显示完整的 `+` 内容。

## 总结原则

### 取最终状态，忽略中间过程

对于上下游来说，只关心从最开始到结束的净改动。不描述中间的反复修改。

- 错误：「r507007 新增 GMShow 为 FName，r507371 改为 FString」
- 正确：「新增 GMShow 字段（FString 类型）」

### 跳过琐碎变更

以下内容不需要出现在总结中：
- 注册表名（如修改 DataNames.lua）
- DataMgr 接入的标准套路（include、CleanUp、LoadAllKeys、DataTableMap 注册）
- 导表生成的标准模板代码
- 纯格式调整、换行符修正

### 只写有业务意义的改动

聚焦代码做了什么、提供了什么能力，而不是怎么做的实现细节堆砌。

## 代码审查

审查针对净改动（第 2 步的 diff），聚焦"改动带来的影响"，而非泛泛的风格挑刺。

### 审查重点

针对本项目（UE4 C++ + Lua/UnLua）的高频问题：

- **依赖与加载**：全局 `_G.XXX` 移除/新增后调用点是否全部迁移；require 增删是否对称；是否存在循环依赖；加载顺序耦合。
- **正确性**：nil / 空表判断、边界条件、off-by-one；Lua 的 `:` vs `.` 调用（self 绑定）；作用域泄漏；反射/字符串拼接的字段名是否仍能命中定义。
- **提交卫生**：commit message 与实际改动是否一致；是否混入不相关改动；是否误删本应保留的内容。

### 严重度分级

- `阻塞`：会导致报错、运行时崩溃、功能不可用、编译失败 —— 必须改才能合入
- `建议`：不影响正确性，但值得改进（风格、一致性、可维护性）
- 若无问题，明确说明已验证项与置信度

## 输出格式

```markdown
**改动概述**

一段话概括本次改动做了什么。

**核心改动**

1. 第一项：做了什么，对外提供什么能力。
2. 第二项：做了什么，关键机制是什么。
3. ...

**测试点**

1. 第一个验证点：怎么测，预期什么。
2. 第二个验证点：怎么测，预期什么。
3. ...

**代码审查**

结论：[可合入 / 有阻塞需修改 / 低风险可合入] —— 一句话总评。

阻塞：
1. [文件:行号] 问题描述 → 为什么是阻塞 → 建议改法
2. ...

建议：
1. [文件:行号] 问题描述 → 建议
2. ...

已验证：
- 用 rg 确认 XxxUtils 全树引用 N 处，均已迁移 / require 链无循环依赖
- ...
```

### 核心改动要求

- 每项聚焦一个功能点或能力点。
- 不超过 6 项，多了说明粒度太细。
- 用「做了什么」而非「怎么做的」来描述。

### 测试点要求

- 每个对应一个可验证的行为。
- 覆盖正常路径、边界条件、异常情况。
- 描述具体操作和预期结果。

### 代码审查要求

- **引用**：每个问题给出具体 `文件:行号`（仓库相对路径）。
- **证据**：结论基于已查到的 diff 或 `rg` 结果，不凭空臆断；无法确认时写明"未确认"。
- 阻塞项在前，建议项在后；无问题时给"已验证"清单与置信度。
- 不复述 diff 内容，只讲问题和风险。
