# 测试用例 Review

## 用例数据格式说明

| 字段 | 类型 | 说明                         |
|:------:|:------:|:----------------------------:|
| `id` | int | 用例 ID                      |
| `name` | string | 用例名                  |
| `parent_id` | int | 所属路径/模块 ID                 |
| `priority` | int | 优先级                        |
| `status` | int | 用例状态                       |
| `action` | string | 操作步骤                 |
| `result` | string | 预期结果                 |
| `condition` | string | 前置条件                 |
| `description` | string | 备注                   |
| `special` | string | 特殊步骤值                      |
| `special_info` | object | 特殊步骤扩展信息，用于记录单个用例是否添加了特殊步骤 |
| `created_by` | string | 创建人邮箱                      |
| `updated_by` | string | 修改人邮箱                      |
| `update_time` | string | 更新时间（ISO 8601）             |
| `is_disabled` | bool | 是否已删除                      |

其中 name, action, result, condition数据都是以html标签的形式，Review时必须忽略tag标签

## 使用场景

当用户需要评审用例平台上的游戏测试用例数据时，使用本 Skill。当前仅支持用例平台导出的用例数据数组。

- 输入必须是用例平台上的用例数据，字段格式见“用例数据格式说明”。
- 如果用户提供需求文档、测试点清单、测试矩阵、自然语言描述、截图或其他非平台用例数据，不要开始 Review，直接提示：`目前仅支持用例平台上用例数据的 Review`。
- 用户要求“帮我 review 测试用例”“看看有没有漏测”“按黑盒方法补充用例”时，也必须先确认输入是平台用例数据数组。

## 输入说明

- 格式为数组
- 单个数组元素格式见 用例数据格式说明  
- 仅支持用例平台上的用例数据数组；其他形式的输入不进入 Review 流程，统一提示：`目前仅支持用例平台上用例数据的 Review`。

## Review 目标

评审时重点判断：

1. 用例是否覆盖玩法规则、隐含约束、异常路径和反作弊相关风险。
2. 黑盒测试方法是否使用充分，是否只测了主流程与理想输入。
3. 客户端与服务端一致性、联机状态、数值边界、资源加载与多端兼容是否覆盖。
4. 用例是否可执行、可验证，前置条件清晰，预期结果可观测（UI、日志、状态、掉落、奖励）。
5. 是否存在重复、模糊、不可测、粒度过粗、缺少关键断言或验收指标的问题。
6. 是否考虑与用例池中其他系统（背包、任务、活动、商店、匹配、战斗等）的耦合影响。

## 信息不足时不要停止工作

如果提示词只给了用例（没有需求、验收标准或规则说明），直接开始 Review，基于可用 case 池和黑盒测试方法完成评审，不等待用户补充信息后再开始。

- 缺少原始需求时，先从用例标题、前置条件、步骤、预期结果中反推业务规则与测试对象。
- 确认输入是用例平台上的用例数据数组后，执行 `gen_case_pool()` 获取全部可用用例并建立对照池。
- 按黑盒方法优先检查：等价类、边界值、判定表、状态迁移、场景法、错误推测。
- 优先输出可立即落地的问题和补充建议；同一用例存在多条修改建议时，先合并为一条待回写 HTML，暂存到最终回写清单，禁止在分析过程中调用 `add_review_record`。

不要因为信息不足就停止工作；先给出可判断的问题和需要补充的信息。

## Review 流程

按下面顺序评审：

1. 先判断用户输入是否为用例平台上的用例数据数组；如果不是，停止 Review，不执行 `gen_case_pool()`，不执行 `add_review_record`，只回复：`目前仅支持用例平台上用例数据的 Review`。
2. 开始 review 时，执行 `gen_case_pool()` 拉取全部路径下的可用 case，作为本次评审用例池。
3. 提取“用户输入 case_id 集合”：
   - 只把用户本次输入数组中明确包含的 `id` 视为允许回写的 `case_id`；从 `gen_case_pool()` 获取到的其他用例只能作为对照池，不属于允许回写范围。
4. 对照 case 池中的用例，标记已覆盖、部分覆盖、未覆盖和不可判断的内容。
5. 使用黑盒方法检查遗漏：等价类、边界值、判定表、状态迁移、场景法、错误推测。
6. 检查用例质量：标题、前置条件、步骤、测试数据、预期结果、断言、优先级。
7. 针对每条需要修改建议的用例，生成具体、可执行的建议文本（不能只给笼统结论）；同一用例的多条修改点必须合并成一条建议。
8. 建立最终回写清单：以 `case_id` 为唯一 key，仅收录“用户输入 case_id 集合”内的用例；同一 `case_id` 无论出现多少问题、多少建议来源，都必须先合并成一个 `suggestion`，最终清单中只能保留一条记录。如果问题来自 case 池中非用户输入的用例，只能在聊天结果中作为参考说明，禁止加入最终回写清单。
9. 汇总输出问题清单、补充建议和可直接落地的新增用例方向。
10. 进入唯一回写阶段：本阶段最多只能发起一次终端命令；命令必须使用 `add_review_records` 批量 action 根据最终回写清单完成回写，同一 `case_id` 在本次 review 中只能写入一次；调用成功后视为已回写，禁止因输出总结、补充说明或同一问题重复调用。

## 自动化执行约束

- 确认用户输入是用例平台上的用例数据数组后，执行 `gen_case_pool()` 必须在每次 review 开始时先执行一次，禁止跳过后直接评审单条用例；如果输入不是平台用例数据数组，不执行该命令，直接提示不支持。命令行如下:

```bash
uv run operate-case --action gen_case_pool
```

- 当提示词只给用例时，禁止等待补充需求再启动；必须立即按 case 池 + 黑盒方法执行评审。
- 所有 `uv run operate-case ...` 命令必须在本 Skill 目录（包含 `pyproject.toml` 的项目根目录）执行；Linux/macOS 下禁止直接执行 `scripts/operate_case.py` 文件路径，避免因缺少 shebang 或可执行权限失败。
- review 对象是用户明确限定的用例范围，在提示词中以数组的形式存在；`add_review_record` 的 `case_id` 只能来自用户本次输入数组中的 `id`。
- `gen_case_pool()` 返回的其他用例只用于覆盖对照、重复性判断和遗漏分析，禁止对这些非用户输入用例执行 `add_review_record`。
- 如果最终回写清单里出现不在用户输入中的 `case_id`，必须先删除该记录再执行命令；不要为了“顺手修正”或“发现了明显问题”给非输入用例添加评论。
- 回写分两步：先生成“最终回写清单”，再执行回写命令；禁止在生成分析结论、整理问题清单或补充测试点时提前调用 `add_review_record`。
- 生成建议时必须绑定具体 `case_id`，做到“一个 `case_id` 对应一条回写记录”；同一用例的多条修改建议必须合并到同一个 `suggestion` 中。
- 建议内容必须基于黑盒测试方法给出明确补充点，例如缺失的等价类、边界值、状态迁移或异常分支。
- 执行回写命令前必须自检：最终回写清单中的 `case_id` 已去重，任意 `case_id` 只能出现一次；终端命令数量必须为 0 或 1，禁止按 `case_id` 拆成多条命令；如果某个 `case_id` 已经执行过回写，本次 review 内不得再次执行。
- 最终执行数据中的 `records` 必须满足 `case_id` 唯一；如果发现重复 `case_id`，必须先合并 `suggestion` 并删除重复记录，再执行 `add_review_records`。
- 并发执行多个 Review 时，只有在各 Review 的“用户输入 case_id 集合”互不重叠时才允许并发回写；如果存在相同 `case_id`，必须串行处理并合并建议后只回写一次，避免后写覆盖前写。
- 禁止使用 `python3 scripts/operate_case.py --action add_review_record --case-id ... --suggestion ...` 逐条回写；也禁止连续多次执行 `uv run operate-case --action add_review_record ...`；禁止使用 `uv run python -c "..."` 内联 Python 执行最终回写。
- 写入建议时仅在最终回写阶段统一通过 `add_review_records` action，不要只在聊天中给建议而不回写平台数据。
- 每条记录的 `suggestion` 必须是 HTML 字符串；如果有多条修改建议，使用一个 `<p>` 搭配 `<br/>` 或 `<ul><li>...</li></ul>` 合并表达。禁止对同一 `case_id` 多次写入，也禁止因同一用例同时出现在多个输出字段中重复调用。例如：`<p>【AI Review】建议补充金币为 0、1、上限、上限 + 1 的边界校验。</p>`。
- 最终回写清单不为空时，必须使用一条 `add_review_records` 命令统一回写；`records-json` 是 JSON 数组，每个元素包含唯一 `case_id` 与 HTML `suggestion`。仅当 JSON 内容较短时使用 `--records-json`，避免触发 shell 命令长度限制：

```bash
uv run operate-case --action add_review_records --records-json '[{"case_id":123,"suggestion":"<p>【AI Review】</p><ul><li>建议补充金币为 0、1、上限、上限 + 1 的边界校验。</li><li>建议补充异常金币值被拒绝后，UI 提示、服务端状态和日志记录一致性的断言。</li></ul>"},{"case_id":456,"suggestion":"<p>【AI Review】建议补充重复领奖拦截校验。</p>"}]'
```

- 如果 JSON 内容较长、记录较多，或当前 shell 对 JSON 引号解析不稳定，先将最终回写清单保存为 UTF-8 JSON 文件，文件名必须包含本次 Review 的唯一标识（例如时间戳、进程号或短随机串），再只发起一次终端命令读取文件回写；不要用固定的 `review_records.json`，避免并发 Review 互相覆盖；也不要用 `echo '长 JSON' | ...`，因为长 JSON 仍会占用 shell 命令长度：

```bash
uv run operate-case --action add_review_records --records-file review_records_20260730_151500_a1b2.json
```

## 黑盒方法检查点

### 等价类划分

检查是否覆盖：

- 有效等价类：合法输入、合法组合、常见业务数据、合法操作链路、典型玩家路径（新手、活跃、回流、高等级）。
- 无效等价类：空值、格式错误、类型错误、超长、非法字符、越权数据、非法参数、越权行为、重复领取、客户端伪造请求、异常资源状态。
- 特殊等价类：重复值、历史数据、已停用数据、跨组织或跨租户数据、断线重连、跨天跨周、赛季切换、活动切换、老账号继承、跨服场景。

评审提示：

- 如果仅测了“正常玩家行为”，通常要补充异常操作、重复操作、边界玩家行为和恶意输入。
- 如果多个系统存在联动约束（任务、背包、战斗、活动），不能只单独测单字段或单系统。

### 边界值分析

检查是否覆盖：

- 最小值、最大值、刚好等于边界。
- 小于最小值、大于最大值。
- 长度边界：0、1、最大长度、最大长度 + 1。
- 时间边界：开服时间、活动开始/结束、跨天刷新、跨周结算、按月刷新（闰年问题）、赛季切换。
- 数值边界：体力、金币、钻石、伤害、血量、掉率、等级经验、背包容量上限。

评审提示：

- 只测中间值通常不足，尤其是经济与战斗数值。
- 涉及列表或分页时，要检查首项、末项、空结果、超上限、滚动加载和筛选切换。

### 判定表与组合规则

当需求存在多个条件共同决定结果时，使用判定表检查：

- 条件是否完整列出。
- 每种条件组合是否有期望动作。
- 是否存在互斥条件、优先级条件或默认分支。
- 是否覆盖“条件 A 满足但条件 B 不满足”的负向组合。

适合场景：

- 掉落与奖励发放规则、任务完成规则、匹配分组规则、战斗结算规则、活动参与规则。

### 因果图

当输入条件之间存在依赖、互斥、包含或组合触发关系时，使用因果关系检查：

- 一个输入是否会触发多个输出。
- 多个输入是否共同触发一个输出。
- 某些输入是否不能同时出现。
- 某些输入是否必须成对出现。

评审提示：

- 重点找“条件组合遗漏”和“冲突条件未测”。

### 状态迁移

当对象有状态时，检查是否覆盖：

- 每个合法状态到合法目标状态的迁移。
- 非法状态迁移是否被拦截。
- 重复操作、回退操作、取消操作、超时操作。
- 状态变化后的可见性、权限、通知、日志和数据一致性。

适合场景：

- 账号登录态、匹配房间、对局流程、任务状态、活动状态、战斗状态、存档状态。

### 场景法

检查是否覆盖完整用户路径：

- 主成功流程。
- 可替代流程（不同职业、不同阵容、不同设备操作）。
- 中断后恢复（切后台、断网、重连、重启游戏）。
- 异常分支（资源加载失败、匹配超时、结算失败、发奖失败）。
- 多角色协作流程（组队、房主切换、队员掉线、观战）。
- 前后置系统联动（战斗-任务-成就-背包-邮件-排行榜）。

评审提示：

- 场景用例要能串起真实业务，而不是只验证单个控件。

### 错误推测

结合经验补充容易遗漏的问题：

- 连续点击、连点技能、快速切场景、重复领奖、重复购买。
- 网络抖动、丢包、高延迟、断网重连、弱网下部分成功。
- 并发操作导致重复扣费、重复发奖、状态回滚异常、客户端服务端不一致。
- 切后台、锁屏、切账号、多端登录后继续操作。
- 资源缺失、热更中断、包体版本不一致、配置表版本不一致。

## 用例质量检查

每条用例应满足：

- 标题能说明被测行为和条件。
- 前置条件明确，不依赖口头说明。
- 测试数据具体，不只写“输入合法数据”，要体现具体化的玩家状态、账号等级、道具与数值基线。
- 操作步骤可执行，避免“正常操作”等模糊描述，必要时注明机型、网络环境、帧率档位。
- 预期结果可验证，包含 UI 表现、服务端状态、日志/埋点、奖励发放、数值变化与回滚。
- 正向、反向、边界、联机、兼容性、性能、稳定性等标签或优先级清晰。

## 输出格式

默认按下面格式输出 Review 结果：

```json
{
  "conclusion": "整体评价：覆盖是否充分、主要风险是什么",
  "major_issues": [
    {
      "severity": "高|中|低",
      "description": "问题描述",
      "impact": "影响是什么",
      "suggestion": "建议如何修正"
    }
  ],
  "missing_test_points": [
    {
      "method": "等价类|边界值|判定表|状态迁移|场景法|错误推测",
      "scenario": "遗漏场景",
      "suggestion": "建议补充的测试条件和预期结果"
    }
  ]
}
```

字段含义：

- `conclusion`：本次 Review 的总体结论，说明当前用例覆盖是否充分、主要风险集中在哪些模块或测试方法上。
- `major_issues`：影响较大的问题清单，用于记录可能导致漏测、误测、不可执行或上线风险的问题。
  - `severity`：问题严重程度，取值为 `高`、`中`、`低`。
  - `description`：问题本身的具体描述，要指出当前用例缺了什么、错在哪里或为什么不可验证。
  - `impact`：问题可能带来的影响，例如核心玩法漏测、异常路径未覆盖、线上缺陷逃逸或回归验证困难。
  - `suggestion`：针对该问题的修正建议，必须具体到可执行的补充条件、步骤、断言或预期结果。
- `missing_test_points`：按黑盒测试方法归类的遗漏测试点，用于说明现有用例还没有覆盖哪些输入、边界、组合、状态或场景。
  - `method`：发现遗漏所依据的黑盒方法，取值为 `等价类`、`边界值`、`判定表`、`状态迁移`、`场景法`、`错误推测`。
  - `scenario`：遗漏的具体业务场景或测试条件。
  - `suggestion`：建议补充的测试条件、操作路径和预期结果。

严重程度使用：

- `高`：可能导致核心需求漏测、严重业务风险、上线阻塞。
- `中`：覆盖不完整或断言不清，可能影响缺陷发现。
- `低`：表达、结构、重复度或可维护性问题。

## 新增用例建议格式

当用户要求补充用例时，使用下面格式：

```json
[
  {
    "title": "用例标题",
    "method": "等价类|边界值|判定表|状态迁移|场景法|错误推测",
    "precondition": "前置条件",
    "test_data": "测试数据",
    "steps": [
      "步骤1",
      "步骤2"
    ],
    "expected_result": "预期结果/断言",
    "priority": "P0|P1|P2"
  }
]
```

如果输出大量用例，优先按模块或风险分组，不要堆砌重复组合。

## Review 注意事项

- 先指出真实风险，再给优化建议。
- 不要只说“建议增加边界值测试”，要说明具体边界是什么。
- 不要把白盒实现细节当作必要前提，除非用户提供了代码或内部设计。
- 忽略富文本标签、HTML 标签、HTML 转义符等展示层残留；除非它们直接导致步骤、预期结果或关键业务语义无法理解，否则不要作为问题输出，也不要写入 `add_review_record`。

- 对于协议测试，除输入输出外，还要检查错误码、幂等性、防重、防刷、数据一致性与重放风险。
- 对于 UI 测试，除交互外，还要检查多分辨率适配、多语言超框、手柄/触屏输入差异和引导可达性。
- 对于流程测试，优先覆盖登录、匹配、战斗、结算、发奖、存档、重连、回档和异常恢复。
- 对于系统模块测试，重点关注存盘读档、热更后兼容、客户端与服务端属性一致性，埋点日志是否覆盖。
- 对于战斗模块测试，必须覆盖单机与联机、不同网络质量、不同帧率和断线重连下的行为一致性。
- 对于资产测试，重点关注多平台兼容、资源加载时序、内存占用、贴图与特效降级表现。
- 对于关卡测试，重点关注导航网格、触发器、刷怪点、场景加卸载、上下线和跨场景数据恢复。
